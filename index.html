Token Lab

How a language model actually reads your text, and what it forgets when the conversation gets long. About 45 minutes, self-paced.

Models don't read words

A language model never sees letters or words. It sees a list of integers called tokens. A tokenizer chops your text into pieces from a fixed vocabulary, and each piece gets an ID number. Everything that follows (cost, speed, limits, some odd mistakes) comes from this one step.

Why you should care when building apps
  • Money: APIs bill per token, not per word.
  • Limits: the context window is measured in tokens. Overflow it and old text is lost or the call fails.
  • Fairness: the same sentence can cost 3x more in Tamil than in English. You will measure this yourself in Part 2.
Rule of thumb for English: 1 token is about 4 characters, or 3/4 of a word. Treat it as a rough guide. Each model family uses its own tokenizer, so counts differ.
By the end you will be able to
  • Explain how BPE builds a vocabulary from data.
  • Predict roughly how many tokens a text will use, and why some languages cost more.
  • Choose a memory strategy when a conversation outgrows the context window.
  • Split a token budget between prompt, history, retrieved documents and answer.

Your path: (1) build a tokenizer by hand, (2) test it on real text, (3) watch a chatbot run out of memory, (4) fix it, (5) plan a token budget, (6) quiz.

Part 1: How a tokenizer is built (BPE)

Most modern models use Byte Pair Encoding. The idea is simple: start with single characters, then repeatedly merge the most frequent neighbouring pair into one new token. Common chunks like "est" or "ing" become single tokens. Rare words stay split up.

Part 3: The context window

The context window is the maximum number of tokens a model can look at in one call: system prompt + conversation history + any documents + the answer it writes. The model has no memory between calls. Your app resends the history every time, and when it no longer fits, something must be dropped.

Challenge: the user said they are allergic to peanuts in message 1. With all 8 messages sent, find a window size and strategy where the bot stays safe. Then find the smallest window where each strategy still works.

What you just saw:
• Dropping oldest is cheap but loses key facts, which is a real safety bug.
• Pinning keeps important instructions but needs you to know what's important.
• Summarising compresses history. In production an extra LLM call writes the summary, which costs money and can lose details. Real systems often combine all three, and also store facts in a database to retrieve later.

Part 4: Challenge, budget a support bot

You are building a customer-support bot on a model with an 8,000-token window. Split the budget so the call fits and meets these requirements:

  • System prompt: at least 300 tokens
  • Retrieved help-article chunks: at least 1,500 tokens (about 3 chunks)
  • Reserved for the answer: at least 800 tokens
  • Total must not exceed 8,000

Gotcha: the output counts against the window. If you fill 8,000 with input, the model has no room to answer and the reply is cut off mid-sentence. Always reserve output space first.

Apply it: real code

This is the trimming logic most chat apps need. It uses OpenAI's tiktoken library, which you can run locally. For other providers, use their own token-counting tool.

import tiktoken
enc = tiktoken.get_encoding("cl100k_base")

def count(text): return len(enc.encode(text))

def fit_history(system, messages, window=8000, reserve_out=1000):
    budget = window - reserve_out - count(system)
    kept, used = [], 0
    for m in reversed(messages):
        n = count(m["content"])
        if used + n > budget: break
        kept.insert(0, m); used += n
    return [{"role": "system", "content": system}] + kept
Extension ideas: pin a "user profile" message, summarise the dropped part, then run the function against a 50-message conversation and print what was dropped.
